## `impress-scenario-service_scenario-create`

Store a spec as a new `impress/scenario@1.0.0` row, after validating it exactly as `scenario_validate` does. Refused `invalid-spec` with every problem when any is found; nothing is stored.

- **safety**: `mutating`
- **reads**: "impress/scenario@1.0.0"
- **writes**: "impress/scenario@1.0.0"
- **reach**: —

| Argument | Type | Required | Description |
|---|---|---|---|
| `spec` | — | yes | The scenario spec, as JSON. Validated first; refused with every problem if any is found. |
| `tags` | — | no | Free-text labels. |

**Examples**

- `default`:

  ```json
  {"spec": {"wire_version": 1, "id": "example.noop", "description": "a scenario with one no-op step", "tier": "a", "steps": [{"call": "impress-scenario-service_scenario-list", "args": {}, "as": "agent:scenario"}]}}
  ```

## `impress-scenario-service_scenario-run`

Run one stored scenario by its `scenario_id`, Tier A on a fresh scratch store or Tier B against `base_url` (default: this device's own app, resolved the way the layout Tier B catalogue does). `external`: a Tier B run leaves the process over loopback HTTP, and a scenario's steps may call any verb, including a mutating or destructive one — the same reasoning that makes `workflow-service_run` (and every other "run arbitrary steps" verb) an external safety class rather than trying to infer a tighter one from what happens to run.

- **safety**: `external`
- **reads**: "impress/scenario@1.0.0"
- **writes**: any("a scenario's steps may call any verb, including a mutating one")
- **reach**: network

| Argument | Type | Required | Description |
|---|---|---|---|
| `base_url` | — | no | The app's loopback base URL for a Tier B run (this device's impress by default). |
| `scenario_id` | string | yes | The scenario's stable `scenario_id`. |
| `tier` | — | no | `"a"` or `"b"`; the scenario's own declared tier when absent. |

_No examples yet._
